บทที่ 1

Introduction to Database & SQL Review

Database (ฐานข้อมูล) คือ กลุ่มของข้อมูลที่มีความสัมพันธ์กันอย่างมีตรรกะ (Logically related data) พร้อมคำอธิบายโครงสร้างข้อมูล (Metadata) ที่เก็บไว้ใช้ร่วมกันภายในองค์กร โดยมีคุณสมบัติ Persistent Data (ข้อมูลคงอยู่ถาวรแม้โปรแกรมที่สร้างจะปิดไปแล้ว)

1. กลุ่มคำสั่ง SQL ทั้ง 4 ประเภท

  • DDL (Data Definition Language): นิยามและแก้ไขโครงสร้างตาราง ได้แก่ CREATE, ALTER, DROP
  • DML (Data Manipulation Language): จัดการข้อมูลในตาราง ได้แก่ SELECT, INSERT, UPDATE, DELETE
  • DCL (Data Control Language): ควบคุมสิทธิ์การเข้าถึง ได้แก่ GRANT, REVOKE
  • Transaction Control: ควบคุมทรานแซคชัน ได้แก่ COMMIT, ROLLBACK, SAVEPOINT, SET ISOLATION

2. ประเภทของข้อมูล & บทบาทบุคลากร (Actors)

  • Structured Data: ข้อมูลที่มีโครงสร้างตารางชัดเจน จัดการด้วย RDBMS (MySQL, PostgreSQL, Oracle, SQL Server, SQLite)
  • Semi-structured Data: ข้อมูลกึ่งโครงสร้าง เช่น XML, JSON
  • Unstructured Data: ข้อมูลไร้โครงสร้าง เช่น วิดีโอ, เสียง, รูปภาพ, เอกสาร, อีเมล (มักใช้ NoSQL เช่น MongoDB, Redis, Apache HBase, Cassandra)
  • Metadata / Data Dictionary / System Catalog: คำอธิบายของข้อมูล (Self-describing nature) เก็บชื่อตาราง คอลัมน์ ชนิดข้อมูล และ Constraints
  • Actors ในระบบฐานข้อมูล:
    • Data Administrator (DA): วางแผนระบบ (System Planning) และกำหนดนิยามข้อมูลระดับนโยบาย
    • Database Designer / Analyst: เก็บรวบรวม Requirement จากผู้ใช้ และออกแบบฐานข้อมูล
    • Database Administrator (DBA): ตั้งค่าระบบ (Config), ดูแลรักษา และปรับจูนประสิทธิภาพ (Maintain/Tune)
    • Application Developer / Programmer: เขียนโปรแกรมเชื่อมต่อฐานข้อมูล
    • End User: ผู้ให้ข้อมูลความต้องการและใช้งานระบบ
📌 จุดเน้นจากอาจารย์ในคลาส (Week 1 - 3):
  • หลักการ JOIN: ถ้าข้อมูลที่ต้องการมีครบในตารางเดียวอยู่แล้ว "ไม่ต้อง JOIN" (เช่น หายอดรวมแต่ละออเดอร์จาก SUM(quantityOrdered * priceEach) และ GROUP BY orderNumber สามารถดึงจากตาราง orderdetails ตารางเดียวได้เลย)
  • WHERE vs HAVING: ห้ามใช้ WHERE กรองค่าที่ได้จากฟังก์ชัน SUM() หรือ COUNT()! ต้องใช้ HAVING เพื่อกรองกลุ่มหลังจาก GROUP BY แล้ว และอาจารย์แนะนำให้เขียน Original Expression หลัง HAVING (เช่น HAVING SUM(quantityOrdered * priceEach) > 50000) แทนการใช้ชื่อ Alias เพื่อให้รันได้ทุก DBMS ตามมาตรฐาน SQL
  • การรวมผลลัพธ์ตารางด้วย UNION: หากต้องการเช็คจำนวนแถว SELECT COUNT(*) ของหลายตารางในการรันครั้งเดียว สามารถใช้ Set Operator คือ UNION เชื่อมกันได้
บทที่ 2

Database Environment & Architecture

1. สถาปัตยกรรม ANSI-SPARC (3-Level Architecture)

ระดับ (Level)Schemaหน้าที่และตัวอย่าง
External LevelExternal Views (มีหลาย View)มุมมองเฉพาะของผู้ใช้แต่ละคน เห็นเฉพาะข้อมูลที่ตนสนใจ (เช่น View แสดง age ที่คำนวณมาจากวันเกิด)
Conceptual LevelConceptual Schemaโครงสร้างเชิงตรรกะของทั้งองค์กร บอกว่าเก็บข้อมูลอะไร (Entities, Attributes, Relationships, Constraints) เช่น เก็บ DOB (วันเกิด)
Internal LevelInternal Schemaโครงสร้างทางกายภาพ (Physical implementation) บอกว่าเก็บลงดิสก์อย่างไรให้เร็วและประหยัดพื้นที่ (เช่น struct, Indexes, Pointers, Data files)

2. Data Independence (ความเป็นอิสระของข้อมูล)

  • Logical Data Independence: การเปลี่ยน Conceptual Schema (เช่น เพิ่มตาราง/คอลัมน์) โดยไม่กระทบต่อ External Views หรือโปรแกรมของผู้ใช้
  • Physical Data Independence: การเปลี่ยน Internal Schema (เช่น สร้าง Index ใหม่, ย้ายไฟล์ข้อมูล) โดยไม่กระทบต่อ Conceptual Schema

3. สถาปัตยกรรม Multi-user DBMS

  • Teleprocessing: ใช้ Mainframe ประมวลผลตรงกลางทั้งหมดผ่าน Dumb Terminals ทำให้คอมพิวเตอร์กลางรับภาระหนักมาก (Network traffic ต่ำ แต่ค่าอุปกรณ์แพง)
  • File-Server: เซิร์ฟเวอร์ส่งทั้งไฟล์ข้อมูลผ่าน LAN มาให้ Workstation ที่มี DBMS ประมวลผลเอง ข้อเสียคือ Network Traffic สูงมาก, ต้องลง DBMS ทุกเครื่อง และคุม Concurrency/Recovery ยาก
  • Two-Tier Client-Server: Tier 1 (Fat Client) จัดการ UI และ Application Logic ส่วน Tier 2 (Database Server) รัน DBMS ประมวลผล SQL, เช็คสิทธิ์ และคุม Integrity
  • Three-Tier Client-Server: แยกเป็น Tier 1 (Thin Client - ใช้ฮาร์ดแวร์ราคาถูก), Tier 2 (Application Server เช่น Tomcat, Nginx, IIS, WebLogic, WildFly, GlassFish รัน Business Logic, ทำ Load Balancing และ Connection Pooling) และ Tier 3 (Database Server)
  • Middleware (ODBC / JDBC): ซอฟต์แวร์ตัวกลางที่ช่วยให้แอปพลิเคชันเชื่อมต่อกับฐานข้อมูลต่างชนิดกัน (Heterogeneous systems) ได้อย่างราบรื่น
บทที่ 3

Relational Model, Keys & Integrity Constraints

คิดค้นโดย Dr. E.F. Codd (IBM, 1970) โดยอ้างอิงจากทฤษฎีเซตทางคณิตศาสตร์

  • Relation = Table | Attribute = Column | Tuple = Row
  • Degree = จำนวนคอลัมน์ (Attributes) ของตาราง | Cardinality = จำนวนแถว (Tuples) ของตาราง
  • Domain = ขอบเขตของค่าที่อนุญาตให้ใส่ในคอลัมน์นั้นๆ
  • ลำดับของแถวและคอลัมน์: ลำดับของ Tuple ไม่สำคัญ แต่เวลาใช้คำสั่ง INSERT INTO table VALUES (...) โดยไม่ระบุรายชื่อคอลัมน์ ลำดับของค่าต้องตรงกับลำดับของ Attribute ในตาราง

ประเภทของ Keys และ Integrity Constraints

  • Superkey: แอตทริบิวต์หรือกลุ่มของแอตทริบิวต์ที่ระบุแถวได้ไม่ซ้ำกัน (อาจมีคอลัมน์เกินความจำเป็นปนอยู่)
  • Candidate Key: Superkey ที่เล็กที่สุด (Minimal superkey) มี 2 คุณสมบัติคือ Uniqueness (ไม่ซ้ำ) และ Irreducibility (ตัดคอลัมน์ใดออกไม่ได้อีก)
  • Primary Key (PK): Candidate Key ที่ถูกเลือกมาเป็นคีย์หลักของตาราง (ห้ามเป็น NULL ตามกฎ Entity Integrity)
  • Alternate Key (AK): Candidate Key ตัวที่ไม่ได้ถูกเลือกเป็น PK (กำหนดด้วย UNIQUE)
  • Surrogate Key: คีย์เทียมที่เป็นตัวเลขรันอัตโนมัติ (AUTO_INCREMENT) ไม่มีผลทางธุรกิจ
  • Foreign Key (FK) & Referential Integrity: คีย์นอกที่อ้างอิงไปยัง PK ของตารางแม่ ค่าของ FK ต้องมีอยู่จริงในตารางแม่ หรือเป็น NULL เท่านั้น การจัดการเมื่อลบ/แก้ไขตารางแม่มี 3 แบบ:
    • RESTRICT (หรือ NO ACTION): ห้ามลบ/แก้ไขตารางแม่ ถ้าตารางลูกยังอ้างอิงอยู่ (เป็นค่าเริ่มต้นหากไม่ระบุ)
    • CASCADE: ลบ/แก้ไขแถวในตารางลูกที่อ้างอิงอยู่ตามตารางแม่โดยอัตโนมัติ
    • SET NULL: เปลี่ยนค่า FK ในตารางลูกให้เป็น NULL (คอลัมน์ FK นั้นห้ามติด NOT NULL)
บทที่ 4 & 5

ER Model (Conceptual) & Logical Database Design

📌 กฎเหล็กจากอาจารย์ในการวาด ER และแปลงเป็นตาราง (Week 4, 6, 7):
  • ใน Conceptual ER Diagram: ระบุเฉพาะ Primary Key {PK} เท่านั้น "ห้ามเขียน Foreign Key (FK) หรือรายละเอียด Constraint ย่อยๆ ลงในกล่อง Entity ของ Conceptual ER เด็ดขาด"
  • การอ่านคำใบ้ Multiplicity จากโจทย์: ถ้าโจทย์ใช้คำว่า "may" (อาจจะ) แปลว่า Participation ขั้นต่ำเป็น 0 (Optional เช่น 0..* หรือ 0..1) แต่ถ้าใช้คำว่า "must" / "exactly one" แปลว่าขั้นต่ำเป็น 1 (Mandatory เช่น 1..1 หรือ 1..*)
  • Composite Attribute (เช่น name แยกเป็น fName, minit, lName): เวลาแปลงเป็นตารางใน Logical Design ให้สร้างเฉพาะคอลัมน์ย่อยสุดเท่านั้น (3 คอลัมน์) ห้ามสร้างคอลัมน์แม่ name!
  • Derived Attribute (มีเครื่องหมาย / นำหน้า เช่น /totalAmount): ไม่ต้องสร้างเป็นคอลัมน์เก็บจริงในตาราง แต่ให้คำนวณผ่าน Query หรือสร้างเป็น VIEW แทน
  • Attribute บนเส้นความสัมพันธ์ (เส้นประชี้ที่เส้น): ถ้าเป็นความสัมพันธ์ *:* จะไปอยู่ในตารางกลางที่สร้างใหม่ แต่ถ้าเป็นความสัมพันธ์ 1:1 หรือ 1:* "Foreign Key ไปอยู่ตารางฝั่งไหน แอตทริบิวต์บนเส้นความสัมพันธ์จะตามไปอยู่ตารางฝั่งนั้นด้วย!"
  • การลากเส้นใน MySQL Workbench: ความสัมพันธ์ปกติ (รวมถึง Self-reference / Recursive) ต้องใช้ เส้นประ (Non-identifying) เท่านั้น ส่วน เส้นทึบ (Identifying) ใช้เฉพาะเมื่อ FK เข้าไปเป็นส่วนหนึ่งของ PK ในตารางลูก (เช่น Weak Entity หรือตารางกลางของ M:N)

สรุปกฎ ER-to-Relational Mapping ทั้ง 7 ข้อ

  1. Strong Entity: สร้างตารางปกติ เอาเฉพาะ Simple attributes (ระดับย่อยสุดของ Composite)
  2. Weak Entity: สร้างตารางใหม่ ดึง PK ของตารางแม่มาเป็น FK และใช้ (PK แม่ + Partial Key ลูก) เป็น Composite PK
  3. 1:1 Relationship:
    • Mandatory ทั้งสองฝั่ง (1..1 - 1..1): ยุบรวมเป็น 1 ตาราง
    • Mandatory ฝั่งเดียว (1..1 - 0..1): เอา PK ของฝั่ง Optional (0..1 - แม่) ไปใส่เป็น FK ในฝั่ง Mandatory (1..1 - ลูก) และตั้งเป็น NOT NULL, UNIQUE เพื่อเลี่ยงค่าว่าง
    • Optional ทั้งสองฝั่ง (0..1 - 0..1): เลือกวาง FK ฝั่งใดก็ได้ตามความเหมาะสม
  4. 1:* Relationship: เอา PK ของฝั่ง One (1) ไปวางเป็น FK ที่ตารางฝั่ง Many (*) เสมอ ถ้าฝั่ง One มี Participation เป็น 1..1 ตัว FK นั้นต้องเป็น NOT NULL
  5. *:* (Many-to-Many) Relationship: สร้างตารางกลาง (Associative Table) ดึง PK ของทั้งสองฝั่งมาเป็น FK และรวมกันเป็น Composite PK (หรือใช้ Surrogate PK + UNIQUE คู่กัน)
  6. Multi-valued Attribute (เช่น telNo [1..3]): แยกไปสร้างตารางใหม่ ใช้ (PK ของตารางหลัก + ค่าของแอตทริบิวต์นั้น) เป็น Composite PK
  7. N-ary Relationship ($n > 2$): สร้างตารางกลางใหม่ ดึง PK ของทุก Entity ที่เข้าร่วมมาเป็น FK

Enhanced ER Diagram (Specialization / Generalization)

Subclass จะสืบทอด (Inherit) แอตทริบิวต์และ Primary Key ทั้งหมดมาจาก Superclass เสมอ โดยมีข้อจำกัด 2 ด้านคือ Participation (Mandatory / Optional) และ Disjointness (Disjoint {Or} / Nondisjoint {And})

Optionเงื่อนไข (Constraints)จำนวนตารางที่ต้องสร้างใน Logical Design
Option 1Mandatory, Nondisjoint {And}
(ต้องเป็นคลาสลูก และเป็นได้มากกว่า 1 คลาส)		1 ตารางเดียว (Single relation) รวมทุกคอลัมน์ของตัวแม่และตัวลูก พร้อมใส่ Flag/Discriminator บอกสถานะ
Option 2Optional, Nondisjoint {And}
(ไม่เป็นคลาสลูกก็ได้ แต่ถ้าเป็น เป็นได้หลายคลาส)		2 ตาราง: ตารางที่ 1 สำหรับ Superclass และ ตารางที่ 2 รวมทุก Subclasses เข้าด้วยกันพร้อม Flag
Option 3Mandatory, Disjoint {Or}
(ต้องเป็นคลาสลูก และเป็นได้แค่คลาสเดียวเท่านั้น)		หลายตาราง (เท่าจำนวน Subclass): ยุบคอลัมน์ของ Superclass ลงไปรวมในตารางของแต่ละ Subclass เลย (ไม่มีตาราง Superclass แยก)
Option 4Optional, Disjoint {Or}
(ไม่เป็นคลาสลูกก็ได้ และถ้าเป็นก็เป็นได้แค่คลาสเดียว)		หลายตาราง (1 Superclass + ทุก Subclass): สร้าง 1 ตารางสำหรับ Superclass และสร้างตารางแยกสำหรับแต่ละ Subclass
บทที่ 7 & 8

Normalization (UNF, 1NF, 2NF, 3NF, BCNF)

เป้าหมายหลักคือ ลดความซ้ำซ้อนของข้อมูล (Minimize data redundancy) และป้องกันความผิดปกติจากการปรับปรุงข้อมูล 3 รูปแบบ ได้แก่ Insertion Anomaly, Deletion Anomaly, และ Modification (Update) Anomaly

ขั้นตอนการทำ Normalization

  • UNF (Unnormalized Form): ตารางที่ยังมี Repeating Group หรือเก็บหลายค่าในช่องเดียวกัน
  • 1NF (First Normal Form): ขจัด Repeating Group ให้ทุกช่องเก็บค่าเดี่ยว (Atomic value) ทำได้ 2 วิธีคือ Method 1 (Flattening เติมข้อมูลให้เต็มแถวแล้วใช้ Composite PK) หรือ Method 2 (แยกส่วนที่ซ้ำออกไปเป็นอีกตารางพร้อมสำเนา PK เดิม)
  • 2NF (Second Normal Form): ต้องเป็น 1NF และ ไม่มี Partial Dependency (ไม่มี Non-prime attribute ใดที่ขึ้นอยู่กับแค่ "บางส่วน" ของ Composite PK) หมายเหตุ: ถ้า PK เป็นคอลัมน์เดี่ยว ตารางที่เป็น 1NF จะเป็น 2NF โดยอัตโนมัติ
  • 3NF (Third Normal Form): ต้องเป็น 2NF และ ไม่มี Transitive Dependency (ไม่มี Non-prime attribute ใดที่ขึ้นกับ Non-prime attribute ตัวอื่น เช่น $A \rightarrow B$ และ $B \rightarrow C$ โดยที่ $C$ ไม่ใช่ส่วนหนึ่งของคีย์)
  • BCNF (Boyce-Codd Normal Form): เข้มงวดกว่า 3NF คือ ทุกๆ Determinant (ฝั่งซ้ายของลูกศร $X \rightarrow Y$) จะต้องเป็น Candidate Key เสมอ!
📌 ทริคสำคัญเรื่อง Prime vs Non-Prime Attribute และ BCNF จากอาจารย์ (Week 9):
  • Prime Attribute คือ แอตทริบิวต์ที่เป็นส่วนหนึ่งของ Candidate Key ใดๆ ก็ได้ ส่วน Non-prime Attribute คือ แอตทริบิวต์ทั่วไปที่ไม่ได้อยู่ใน Candidate Key เลย
  • การจะถือว่าผิดกฎ 2NF (Partial) หรือ 3NF (Transitive) ตัวที่อยู่ฝั่งขวามือของลูกศร จะต้องเป็น Non-prime attribute เท่านั้น! ถ้าฝั่งขวามือเป็นส่วนหนึ่งของ Candidate Key (Prime attribute) จะไม่ถือว่าละเมิด 2NF หรือ 3NF แต่จะไปละเมิดกฎที่ระดับ BCNF แทน (เพราะฝั่งซ้ายไม่ใช่ Candidate Key)
  • เมื่อแยกตารางใน BCNF แล้วพบว่ามี FD ที่มี Determinant (ตัวซ้ายมือ) เป็นตัวเดียวกัน (เช่น driver_id -> driver_name และ driver_id -> vehicle_id) ให้ยุบรวมไว้ในตารางเดียวกันได้เลย ไม่ต้องแยกเป็น 2 ตาราง!
บทที่ 9

สรุป 15 ข้อผิดพลาดในการออกแบบฐานข้อมูล (15 Design Mistakes)

  1. Case 1 (Artist Genres): เก็บ Genre1, Genre2, Genre3 หรือคั่นด้วยลูกน้ำ 'Jazz, Soul' ผิด 1NF $\rightarrow$ ต้องแยกเป็นตารางใหม่ ARTIST_GENRE(ArtistID, Genre)
  2. Case 2 (Playlist Totals): เก็บ SongCount และ TotalMinutes เป็นคอลัมน์จริง ทำให้ข้อมูลขัดแย้งเมื่อเพิ่ม/ลบเพลง $\rightarrow$ เป็น Derived Attribute ต้องใช้ Query หรือ VIEW คำนวณแทน
  3. Case 3 (Movies & Actors): ความสัมพันธ์ M:N แต่เอา ActorID ไปใส่ในตาราง MOVIE $\rightarrow$ ต้องสร้างตารางกลาง CAST_MEMBER(MovieID, ActorID)
  4. Case 4 (Airlines & Flights): ความสัมพันธ์ 1:N แต่เอา FlightNo ไปใส่ในฝั่ง One (AIRLINE) $\rightarrow$ ต้องเอา FK (AirlineCode) ไปวางไว้ที่ฝั่ง Many (FLIGHT) และตั้ง NOT NULL
  5. Case 5 (Recipe Quantities): เอาปริมาณวัตถุดิบ (Quantity) ไปไว้ในตาราง INGREDIENT $\rightarrow$ ปริมาณขึ้นอยู่กับทั้งสูตรและวัตถุดิบ ต้องเอาไว้ในตารางกลาง RECIPE_INGREDIENT
  6. Case 6 (Creators & Premium Users): ผู้ใช้เป็นได้ทั้งสองอย่าง (Both) หรือไม่เป็นเลย (Neither) แต่ใช้ {Mandatory, Disjoint} $\rightarrow$ ต้องใช้ {Optional, Nondisjoint (AND)}
  7. Case 7 (Pet Clinic Records): ใช้ชื่อสัตว์เลี้ยง (ซ้ำได้), เบอร์โทรเจ้าของ (เปลี่ยนได้), หรือเลขไมโครชิป (เป็น NULL ได้) เป็น PK $\rightarrow$ ต้องสร้าง Surrogate Key PetID AUTO_INCREMENT เป็น PK และตั้ง UNIQUE ให้ไมโครชิป
  8. Case 8 (Hotel Stays): ใช้แค่ (GuestID, RoomNo) เป็น PK ทำให้ลูกค้าคนเดิมกลับมาพักห้องเดิมซ้ำในอนาคตไม่ได้ $\rightarrow$ ต้องเพิ่ม CheckIn เข้าไปใน PK หรือใช้ StayID เป็น Surrogate PK
  9. Case 9 (Match Statistics): เอา PlayerName, Position มาไว้ในตาราง MATCH_PLAYER(MatchID, PlayerID, ...) เกิด Partial Dependency (ผิด 2NF) $\rightarrow$ แยกตาราง PLAYER ออกมา
  10. Case 10 (Delivery Riders): เก็บ ZoneName, ZoneFee ไว้ในตาราง RIDER เกิด Transitive Dependency (ผิด 3NF) $\rightarrow$ แยกตาราง ZONE ออกมา
  11. Case 11 (Café Prices): ดึงราคาปัจจุบัน (CurrentPrice) มาคำนวณใบเสร็จย้อนหลัง ทำให้ยอดเงินในอดีตเปลี่ยนเมื่อร้านขึ้นราคา $\rightarrow$ ต้องเก็บทั้ง CurrentPrice ในตารางเมนู และบันทึก UnitPrice (ราคาขายจริง ณ ตอนนั้น) ลงในตาราง SALE_ITEM
  12. Case 12 (Expense Claims): ยัดข้อมูลหัวเอกสารและรายการย่อยไว้ในตารางเดียวกัน $\rightarrow$ ต้องแยกเป็นตาราง Master (CLAIM) และ Detail (CLAIM_ITEM) โดยตั้ง FK เป็น ON DELETE CASCADE
  13. Case 13 (Mobile Plan History): ใช้ UPDATE ทับแพ็กเกจเดิมทำให้ประวัติเก่าหาย $\rightarrow$ ต้องสร้างตารางประวัติแยก SUBSCRIPTION(SubscriberID, StartDate, PackageID, EndDate)
  14. Case 14 (Ticket Sales): ใช้ VARCHAR เก็บวันที่และจำนวน, ใช้ FLOAT เก็บเงิน (บวกเลขทศนิยมคลาดเคลื่อน และเรียงลำดับผิด) $\rightarrow$ ต้องใช้ DATE สำหรับวันที่, DECIMAL(10,2) สำหรับเงิน, และ INT สำหรับจำนวนนับ
  15. Case 15 (Fitness Club Members): ใช้ INT เก็บรหัสสมาชิก 00412 และเบอร์โทร (ทำให้เลข 0 นำหน้าหาย และใส่ + หรือ - ไม่ได้), ใช้ CHAR(255) เก็บชื่อ, ใช้ VARCHAR เก็บสถานะ $\rightarrow$ ต้องใช้ CHAR(5) เก็บรหัสคงที่, VARCHAR(15) เก็บเบอร์โทร, VARCHAR(100) เก็บชื่อ, และ BOOLEAN เก็บสถานะ
Lab 10 & SQL

SQL DDL, Naming Convention & Automatic Timestamps

  • ลำดับการสร้างและลบตาราง (Creation & Drop Order):
    • การสร้าง (CREATE): ต้องสร้าง Parent Table (ตารางแม่ที่ไม่มี FK) ก่อน แล้วจึงสร้าง Child Table (ตารางลูกที่มี FK อ้างอิงตารางแม่)
    • การลบ (DROP): ต้องลบ Child Table (ตารางลูก) ก่อน แล้วจึงลบ Parent Table (ตารางแม่)
  • มาตรฐานการตั้งชื่อ Constraint (Guideline ใน Lab 10): รูปแบบ <prefix>_<table>_<column> ตัวพิมพ์เล็กทั้งหมด คั่นด้วยขีดล่าง ความยาวไม่เกิน 64 ตัวอักษร เช่น pk_member_member_id, uk_room_type_name, ck_room_type_rate, fk_booking_member_id
  • ข้อสังเกต NOT NULL (จากอาจารย์ Week 10): NOT NULL ต้องเขียนต่อท้าย Data Type ของคอลัมน์นั้นๆ โดยตรง ไม่สามารถแยกมาเขียนเป็น Table-level constraint ด้านล่างเหมือน PRIMARY KEY, UNIQUE, CHECK หรือ FOREIGN KEY ได้
  • การกำหนดเวลาอัตโนมัติ (Auditing Timestamps - BR6): 
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
    • เมื่อ INSERT แถวใหม่: ทั้ง created_at และ updated_at จะได้เวลาปัจจุบันโดยอัตโนมัติ
    • เมื่อ UPDATE แก้ไขค่าในคอลัมน์อื่นให้เปลี่ยนไปจากค่าเดิม: เฉพาะ updated_at จะเปลี่ยนเป็นเวลาใหม่ ส่วน created_at คงเดิม
    • จุดออกสอบสำคัญ (Lab 10 Task 5.3): ถ้ารันคำสั่ง UPDATE ซ้ำด้วยค่าเดิมเป๊ะๆ (ไม่มีคอลัมน์ไหนในแถวนั้นเปลี่ยนค่าไปจากเดิมเลย) ค่า updated_at จะไม่เปลี่ยนแปลง!
